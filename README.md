# tsrs × Monaco

A TypeScript playground that type checks, compiles and runs TypeScript **entirely in the browser**, using
[`@tsrs/wasm`](https://www.npmjs.com/package/@tsrs/wasm) (tsrs, a Rust port of the TypeScript 7 compiler, built for
WebAssembly) inside [Monaco Editor](https://microsoft.github.io/monaco-editor/). Built with the
[Boba](https://github.com/sholtomaud/boba) framework: Custom Elements, a tiny router and an `EventTarget` store.

Background: [Cloudflare's TypeScript compiler in Rust](https://socket.dev/blog/cloudflare-typescript-rust).

## How it works

```
[ Monaco Editor ]  one model per file: tsconfig.json, src/index.ts, src/greet.ts, …
       │  (1) project files (debounced 400 ms)
       ▼
[ compiler.worker ]  tsc(["-p", "/project/tsconfig.json"], { files, diagnostics: "json" })
       │  (2) JSON diagnostics ──► Monaco markers (squiggles) + Problems panel
       │  (3) emitted dist/*.js ──► JavaScript tab
       ▼
[ run.worker ]  (4) each module → Blob URL (relative imports rewritten), then import(entry)
                    console.* is forwarded back to the Console panel
```

- **Real tsrs API.** `@tsrs/wasm` exposes `tsc(args, options)`, the same command line as `tsc`, over an in-memory
  file system. The playground passes the whole virtual project, including an editable `tsconfig.json`, and reads
  back `result.diagnostics` (UTF-16 positions) and `result.files` (emitted JavaScript). The TypeScript `lib.*.d.ts`
  files are bundled inside `tsrs.wasm`.
- **Off the main thread.** The compiler runs in a module worker (the checker recurses deeply, and a slow check never
  blocks typing). `tsrs.wasm` (~9.8 MB, ~2.9 MB gzipped) is compiled once and instantiated fresh for each check.
- **No Monaco TypeScript service.** Only Monaco's core editor, everyday features and syntax highlighting are loaded,
  so every diagnostic comes from tsrs.
- **Sandboxed execution.** Each Run starts a new worker. Stop (or the next Run) terminates it, so an infinite loop
  never freezes the page. Code runs in a worker, so the default `lib` is `esnext` + `webworker` (no DOM).
- **Tests and plots.** User code gets three globals, typed in each example's `src/playground.d.ts`: `plot()` draws a
  line chart in the Plot panel, and `test()` / `expect()` (a Jest-style subset) register tests that **Test**
  (Ctrl/⌘ + Shift + Enter) runs from every `src/**/*.test.ts`.
- **Examples.** *Hello, types*; *npm: ONNX Runtime Web* (builds a tiny ONNX model in memory and runs it);
  *npm: TensorFlow.js + WebGPU* (fits a line with SGD on WebGPU, falling back to the CPU backend); and
  *Odum: CASH money storage*, a port of H.T. Odum's BASIC minimodel
  (Table I-5): one storage with constant inflow `J` and outflow `K*M`, integrated with Euler's method, with tests
  against its steady state `J/K` and exact solution. `npm test` compiles every example with the real `@tsrs/wasm`
  and runs its tests, so a broken example fails CI. The npm examples need the network, so they are checked by
  `LIVE_CDN=1 npx playwright test e2e/npm-examples.live.spec.ts` instead; the regular e2e suite tests npm support
  against a mocked CDN.
- **fluxkit: physics in plain TypeScript.** [`packages/fluxkit`](packages/fluxkit/README.md) is a built-in
  package of the playground (`import * as fx from 'fluxkit'`, no network). You write a model's parameters,
  state and `rates(s, p, t)` as ordinary TypeScript; fluxkit reads the functions' source, compiles them to a WGSL
  kernel (state structs, RK4 or Euler, steady-state or a stop condition, Kahan-summed f32 updates) and runs one
  GPU thread per swept parameter value, or calls the same functions on the CPU without WebGPU. Vectors and
  rotations are `[x, y, z]` and quaternions through small helpers. The *fluxkit* example has four models: the
  Atwood machine, a bicycle sprint through a planetary hub (its gear matrices solved in plain TypeScript), a
  capacitor charged through R (half the energy is always lost), and a game-style projectile with drag; their
  tests check closed forms, and on WebGPU check every generated kernel against the CPU.
  Its declaration files are generated by `node scripts/build-fluxkit-types.mjs` (checked by `npm test`).
- **Energy flows: WebGPU physics.** Phase 1 of a WebGPU physics and ecology toolkit: WGSL compute kernels,
  integrated with forward Euler, for three energy-flow models. Each runs on the GPU when the browser has WebGPU
  (Chrome, Edge) and on a CPU twin of the same kernel otherwise, which reads the same packed buffers.
  - *Atwood machine* (Odum & Pinkerton, 1955): one thread per load ratio R = M2/M1. With friction proportional to
    speed, the steady useful power R(1 − R)M1²g²/b peaks at R = ½, where the efficiency is 50%. The pulley turns
    by quaternion (`q_update`, `q_multiply`, `q_normalize` in WGSL).
  - *Bicycle hub* (Gardner et al., 2007; Wu & Cheng, 2014): one thread per cadence. The rider's torque
    T = T_max − a·PR drives a planetary hub whose speeds and torques come from 3×3 fundamental-circuit and
    latent-power systems, with gear-mesh losses. Power peaks at T_max/2a in every gear.
  - *Ecosystem* (Li et al., 2010; Collins & Odum, 2000): one workgroup per network integrates dx/dt = Cx + u on
    flat N×N arrays (N ≤ 32) to steady state, then writes the flow matrix A (a_ij = flow from i to j) to the output
    buffer, the hand-off to Phase 2 (emergy). Networks are written in a small linear dialect in a tagged template,
    `ecosystem\`producers -> herbivores = 0.1 * producers\``, parsed into C and u with line:column errors.
    The example is Odum's Silver Springs budget, and a sweep of its grazing.

  The example lives as real files in `examples/energy-flows/`; `node scripts/sync-example.mjs energy-flows`
  bundles them into `src/examples/energy-flows.ts` (`npm test` fails if it's stale). Its tests run in CI under
  Node (CPU), and the e2e suite runs them in Chromium on a SwiftShader WebGPU adapter, including GPU-vs-CPU checks
  of each kernel.
- **npm packages.** Type `import * as ort from 'onnxruntime-web'` and it just works:
  - *Types:* the playground resolves the version on jsDelivr, then follows the package's declaration files
    (relative imports, other packages, `/// <reference>`, falling back to `@types/*`) and fetches only the `.d.ts`
    files the import reaches. They're handed to tsrs as `node_modules/`, so it type checks your code against them.
  - *Runtime:* each bare import in the emitted JavaScript is rewritten to a URL. If the package's browser ES module
    is a self-contained bundle (onnxruntime-web), it loads straight from jsDelivr, so assets it finds with
    `import.meta.url`, like its `.wasm`, load from next to it. Otherwise it loads through esm.sh (tfjs), which
    resolves the package's own dependencies so packages share one copy of, e.g., `@tensorflow/tfjs-core`. The
    Console lists where each import came from.
  - Add a root `package.json` (via **+**) with `dependencies` to pin versions; otherwise imports use `latest`.
    Types and runtime always use the same resolved version.
- **Web apps (Preview).** A project with an `index.html` is a web app: Run serves it in the **Preview** tab
  instead of a worker. The *Web app: Boba template* example is [Boba's app
  template](https://github.com/sholtomaud/boba/tree/main/template), type checked by tsrs. A service worker
  (`public/preview-sw.js`) serves `preview/app/` from the Cache API, standing in for Vite: `src/a.ts` is served
  as its emitted JavaScript (at `src/a.ts` and `src/a.js`), `public/` at the root, `?raw` imports as string
  modules, and `import './a.css'` as a module that adds the stylesheet. Tailwind is compiled in the page by
  `@tailwindcss/browser`, served from the playground. npm imports work as on Run, through an import map in
  `index.html`; a build would bundle them into the app's own origin, so the preview adds just those CDN origins to
  the app's Content-Security-Policy, if it has one. The app's console output, load errors and CSP violations
  appear in the Console. Regenerate the example with `node scripts/sync-boba-example.mjs path/to/boba/template`.
- **Workspace.** A VS Code-style workbench: every example is a project folder in the **Explorer** (activity bar
  on the left; Ctrl/⌘ + B shows and hides it). Open files from any project into tabs; the project of the file
  you're editing is the one that is type checked, run and tested (it's named in the status bar). The Explorer
  creates (with `/` for folders), renames (F2) and deletes files inline, and is driven by the keyboard (arrows,
  Enter). Projects keep their own edits; right-click a project, or use the ☰ menu, to Reset it to its original
  files. **Your own projects** go in a *Projects* section above the examples: New Project (blank, or a fluxkit
  model), Duplicate any project or example, and Delete Project. Only the active project is compiled and run, and
  each project keeps its own Console, Plot and Tests output, so switching projects shows that project's last
  results rather than everything at once. The side bar and the output panel (Ctrl/⌘ + J) resize by dragging their edges.
- **GitHub Actions, in the browser.** The **Workflows** view (activity bar) lists the active project's
  `.github/workflows/*.yml` and runs them for a simulated event (`pull_request`, `push` or `workflow_dispatch`),
  so a broken build shows up before you open a pull request. Jobs run in `needs` order, one matrix combination
  after another, each on a fresh in-memory runner whose workspace `actions/checkout` fills with the project's
  current files. Steps get GitHub's contexts and `${{ }}` expressions, `if:` (with `success()`, `failure()`, …),
  `continue-on-error`, step and job outputs (`$GITHUB_OUTPUT`), `$GITHUB_ENV`, `$GITHUB_STEP_SUMMARY`, workflow
  commands (`::error file=…::`, `::group::`, `::add-mask::`) and local composite actions. `run:` scripts go
  through a small bash (pipes, `&&`/`||`, `if`/`for`, `$(…)`, here-documents, `set -e`) over a virtual file
  system. There is no real npm, node or tsc: those commands are thin shims over the playground's toolchain, and
  they fail where GitHub would. `tsrs-wasm` and `tsc` are a tsrs type check (errors become annotations that open
  the file), available through `npx` (`npx -p @tsrs/wasm tsrs-wasm`, or `npx tsc` when TypeScript is a
  dependency) or an npm script; `npm run` runs `package.json` scripts; `npm ci` needs a `package.json` and a
  lockfile, then does nothing (packages load from CDNs); `node -p`/`-e` one-liners run in the worker with a
  `require()` for the workspace's JSON files. `actions/setup-node` and `cache` are shown greyed out as *not needed
  in the browser*; `upload`/`download-artifact` are emulated; deployments are skipped. Tools that can't run in a
  browser (eslint, playwright, docker, …) pass with a warning, and the run says it was only partly emulated.
  The *hello* example has the starter workflow, and *odum-cash* a fuller one (`model-checks.yml`: jobs that
  `need` each other, a matrix, job outputs, step summaries and an artifact passed between jobs); **+** in the
  Workflows view adds the starter to any project. Both run unchanged on GitHub.
- **The same checks on GitHub (`sholtomaud/tsrs-monaco/ci`).** The starter workflow type checks with the
  playground's compiler, pinned (`npx -y -p @tsrs/wasm@<version> tsrs-wasm -p tsconfig.json --noEmit`; Node only
  runs the WebAssembly), then uses this repository's action ([`ci/action.yml`](ci/action.yml)). The action opens
  the deployed playground's CI page (`ci.html`) in headless Chromium with Playwright and has it type check and
  test the project with the editor's own pipeline: tsrs in its worker, npm types and code from the CDNs, the
  tests in a run worker, WebGPU on SwiftShader. It prints the results with annotations and a step summary, and
  sets `errors`, `passed`, `failed` and (with `entry: true`, which also runs `src/index.ts`) `entry-log`. In the
  Workflows view the step runs the same code (`src/ci/checks.ts`) in this page. Pin `playground-version` to a
  release so a playground update can't change results: a `v*` tag publishes that build under `v/<version>/`
  for good (`release.yml` keeps it on the `pages-releases` branch, and `deploy.yml` adds every release to the
  site). This repository's CI runs the action on its own build (`uses: ./ci`), against the examples.
- **Pull requests (GitHub view).** Sign in with a
  [fine-grained personal access token](https://github.com/settings/personal-access-tokens/new) (Contents,
  Pull requests and, for workflow files, Workflows: read and write). A static page can't use GitHub's OAuth flows
  (the web flow needs a client secret, and the device flow's endpoints don't allow cross-origin requests), so the
  browser calls `api.github.com` directly with your token. The token stays in `sessionStorage` (or
  `localStorage` if you tick *Remember*), is sent only to `api.github.com`, and is never saved with the
  workspace. Link a project to a repository (and optionally a folder of it), or **Open a Repository as a
  Project** to import its text files. The view lists what differs from the base branch (by git blob SHA), and
  **Create Pull Request** first runs the workflows a `pull_request` would trigger; if one fails, the request
  waits until you fix it or choose *Open Anyway*. The change is committed with the Git Data API (blobs → tree →
  commit → branch), so nothing is cloned; without push access the branch goes to your fork. The pull request's
  description lists what the workflows found. All of this lives in `src/github/`, the only code that talks to
  GitHub.
- **Persistence.** The workspace (every project's files, open tabs, expanded folders and layout) is saved to
  `localStorage`.

## Source layout

```
src/
├── compiler/
│   ├── compiler.worker.ts   # runs @tsrs/wasm
│   ├── compiler-client.ts   # promise wrapper, restarts the worker if it crashes
│   ├── diagnostics.ts       # tsrs diagnostics → Monaco ranges
│   └── project.ts           # the virtual project and its default files
├── preview/
│   ├── site.ts              # a web app project → the files the Preview serves
│   └── preview-client.ts    # registers public/preview-sw.js, publishes to the Cache API
├── runtime/
│   ├── run.worker.ts        # executes emitted modules, forwards console output
│   ├── module-graph.ts      # links modules as Blob URLs, dependencies first
│   ├── format.ts            # console argument formatting
│   ├── expect.ts            # expect() matchers for user tests
│   ├── chart.ts             # plot() data and SVG rendering
│   └── runner.ts            # one worker per run, stop()
├── packages/                # npm: type acquisition, CDN URLs, package.json resolution; built-ins (fluxkit)
├── examples/                # example projects (+ a test that compiles and runs them;
│                            #   energy-flows.ts is generated from /examples/energy-flows)
├── actions/                 # GitHub Actions emulator: workflow parsing, ${{ }} expressions, a small bash,
│                            #   npm/npx/tsc/node shims, the job runner, and the browser toolchain
├── github/                  # GitHub: token sign-in, REST client, import, changes and pull requests
├── ci/                      # the CI page (ci.html): the checks the GitHub action runs in the playground
├── editor/monaco.ts         # Monaco set-up (features, languages, workers, theme)
├── workspace/               # projects, file tree, tabs and persistence; file icons; menus
├── store/workspace-store.ts
└── components/
    ├── playground-page/     # the workbench: activity bar, Explorer, Workflows and GitHub views,
    │                        #   editor tabs, output panel, status bar
    ├── about-page/          # "How it works"
    └── nav-page/
```

```
packages/fluxkit/            # the fluxkit package: no dependencies, nothing from the playground
├── src/parse.ts             # a model function's source → syntax tree (the accepted JavaScript subset)
├── src/compile.ts           # syntax tree → typed WGSL (numbers, vectors, rotations, booleans)
├── src/model.ts             # Model: layout, the generated kernel, the CPU integrator, Run
├── src/vec.ts               # vector and quaternion helpers, in JavaScript and WGSL
├── src/engine.ts            # WebGPU engine and CPU fallback
└── test/                    # unit tests (node --test)

examples/energy-flows/src/   # bundled into src/examples/energy-flows.ts
├── engine.ts         # WebGPU engine (one binding layout: params, input, state, output) + CPU fallback
├── quaternion.ts     # WGSL q_multiply / q_normalize / q_update, and their CPU twins
├── matrix.ts         # WGSL flat N×N matrices in workgroup memory, Gaussian elimination
├── atwood.ts         # spec B kernel
├── bicycle.ts        # spec A kernel: planetary hub transmission matrix + spin-up
├── ecosystem.ts      # spec C kernel: one workgroup per network → steady-state A
├── dialect.ts        # the network dialect → C, u, x0
├── flows.ts          # EnergyFlows (the Phase 2 hand-off), held in memory by name
├── silver-springs.ts # Odum's Silver Springs budget, in the dialect
└── *.test.ts         # CPU tests; webgpu.test.ts checks each kernel on the GPU
```

## Scripts

| Script | Description |
| --- | --- |
| `npm start` / `npm run dev` | Vite dev server |
| `npm run build` | Production build into `dist/` |
| `npm test` | Unit tests (`node --test`, run directly on TypeScript) |
| `npm run typecheck` | Type check with TypeScript 7 (`tsc -p .`) |
| `npm run lint` | Lint with [oxlint](https://oxc.rs/docs/guide/usage/linter) |
| `npm run e2e` | Playwright tests against the dev server and the production build |
| `node scripts/sync-example.mjs <name>` | Bundle `examples/<name>/` into `src/examples/<name>.ts` |
| `node scripts/build-fluxkit-types.mjs` | Regenerate fluxkit's declaration files for the playground |
| `node scripts/write-example.ts <name> <dir>` | Write an example project to a folder (e.g. to run the CI action on it) |

Requires Node.js 25+ (as Boba does). Pull requests run CI; pushes to `main` run the same tests and deploy `dist/` to GitHub Pages.

## Limits

- The wasm build is single-threaded; each instance has at most 4 GiB of linear memory (wasm32).
- npm packages need the network (jsDelivr for types and bundles, esm.sh for everything else), and a package's
  first type fetch can take a few seconds (tfjs-core is ~300 small `.d.ts` files; they're cached by the browser
  afterwards). Libraries that need the DOM won't work, because code runs in a worker. Multi-threaded wasm (e.g.
  ONNX Runtime threads) needs a cross-origin isolated page, which GitHub Pages can't provide.
- Circular imports between project files are not supported by the Blob URL linker.
- The workflow emulator runs the project's TypeScript on tsrs, not a real runner: no containers, services,
  Docker or JavaScript actions, other shells (`pwsh`, `python`), or tools that need a machine. Jobs run one at a
  time. Expressions, contexts and the shell cover what CI scripts usually use, not all of bash. A run that relied
  on something it couldn't emulate says so.
- Importing a repository takes at most 400 text files of up to 512 KiB each (binaries are skipped).
- The Preview runs on the playground's origin (its service worker must control the frame), so an app there can
  reach the playground's page and storage. It needs HTTPS or localhost, and the scripts it adds to `index.html`
  (import map, console bridge) need a CSP that allows inline scripts, as Boba's does.
