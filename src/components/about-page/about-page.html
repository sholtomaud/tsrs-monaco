How it works

This playground type checks, compiles and runs TypeScript entirely in your browser. The compiler is tsrs, a Rust port of the TypeScript 7 compiler, shipped to the browser as @tsrs/wasm. Nothing is sent to a server.

  1. 1. Monaco Editor

    Each file in the project is a Monaco model. Monaco provides editing and syntax highlighting only: its bundled TypeScript language service is deliberately left out so every diagnostic you see comes from tsrs.

  2. 2. Type check with @tsrs/wasm

    400 ms after you stop typing, the files are posted to a Web Worker that runs tsc(["-p", "/project/tsconfig.json"], { files, diagnostics: "json" }) over an in-memory file system. The standard library .d.ts files are bundled inside the wasm binary.

  3. 3. Diagnostics become markers

    tsrs returns diagnostics with 0-based lines and UTF-16 columns; they are converted to Monaco's 1-based ranges and set as markers, which draw the red squiggles and fill the Problems panel. Errors in tsconfig.json are reported the same way.

  4. 4. Emit JavaScript

    The same call emits JavaScript into dist/ in memory. The JavaScript tab shows the output for the file you are editing.

  5. 5. Run in a Web Worker

    On Run, the emitted modules go to a fresh module worker. Each module becomes a Blob URL, dependencies first, with relative imports such as ./greet.js rewritten to their Blob URLs, then the entry is loaded with import(). console output is forwarded back to the page. Stop (or the next Run) terminates the worker, so an infinite loop can never freeze the editor.

Tests, plots and examples

Your code gets three globals, typed in each example's src/playground.d.ts: plot(series, options) draws a line chart in the Plot panel, and test(name, fn) with Jest-style expect(value) matchers registers tests. Test (Ctrl/⌘ + Shift + Enter) compiles the project and runs every src/**/*.test.ts file in a fresh worker.

The Odum: CASH money storage example ports Table I-5's BASIC listing, H.T. Odum's simplest energy-systems minimodel: one storage with a constant inflow and an outflow proportional to the storage, dM/dt = J - K*M, integrated with Euler's method like the original M=M+DM*dt loop. Its tests check the result against the steady state J/K and the exact solution.

npm packages

Write import * as ort from 'onnxruntime-web' and the playground fetches what's needed, much as npm install would, but lazily. For types, it resolves the version on jsDelivr and follows the package's declaration files (relative imports, other packages, /// <reference>, @types/*), fetching only the .d.ts files the import reaches. They're handed to tsrs as node_modules/, so you get real type errors against the library.

On Run, each bare import is rewritten to a URL with the same version. A self-contained browser bundle (like onnxruntime-web's) loads straight from jsDelivr, so files it locates with import.meta.url, such as its .wasm, load from next to it. Anything else goes through esm.sh, which resolves the package's own dependencies (so tfjs backends share one tfjs-core). Add a root package.json with dependencies to pin versions.

Limits

  • The wasm build is single-threaded and each instance is capped at 4 GiB of linear memory (wasm32).
  • Your code runs in a worker, so there is no DOM: the default lib is esnext + webworker.
  • npm packages need the network. A package's first type fetch can take a few seconds (the browser caches it afterwards). Libraries that need the DOM won't work in the worker.
  • Circular imports between your files are not supported by the Blob URL linker.
